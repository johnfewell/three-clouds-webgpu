# Contributing

Thanks for looking at the port. This file is the whole contribution guide: what
the project is, how to build and check it, and what a change is expected to
look like.

## What this project is

An unofficial WebGPU / TSL port of
[@takram/three-clouds](https://github.com/takram-design-engineering/three-geospatial)
0.7.6, Shota Matsuda's MIT-licensed volumetric clouds library, for the
[three.js](https://threejs.org/) `WebGPURenderer`.

Two things follow from that, and both matter for a contribution:

- **The original is the specification.** Public property names are kept
  verbatim from the WebGL `CloudsEffect`, and the 1:1 mapping is
  [docs/MIGRATION.md](docs/MIGRATION.md). A change that renames a knob is a
  change to that contract, not a cleanup.
- **Parity is measured, not asserted.** The port is compared against the
  original image by image on a real GPU. A change that makes the picture better
  but different has to say so and say why, because the acceptance thresholds
  will notice.

This port is not affiliated with takram. Contributions here are about the port.

## Development setup

Node 24 and Chrome with WebGPU. pnpm is pinned by `packageManager` in
`package.json`, so Corepack picks the right version:

```bash
git clone https://github.com/johnfewell/three-clouds-webgpu.git
cd three-clouds-webgpu
corepack enable
pnpm install --frozen-lockfile
pnpm build
```

`pnpm build` matters: the examples and the parity harness serve the built
library from `build/`, not `src/`. A capture or a story taken without a rebuild
measures stale code.

The committed `docs/API.md` is checked, not rewritten, by `pnpm check`, packing
and CI. Local `pnpm build` and `pnpm typecheck` do not require fresh documentation.
After changing public declarations, their source positions, JSDoc or defaults,
run `pnpm docs:api` and commit the regenerated reference with the source change.
`pnpm docs:api:check` checks against the current compiled defaults; `pnpm check`
builds first, and packing verifies build freshness before checking the reference.

To look at something rendering:

```bash
pnpm --filter clouds-storybook dev --port 6008
```

The library itself is `src/`. `examples/basic` is the smallest consumer,
`examples/r3f` the React binding, `examples/parity` the A/B harness, and
`examples/storybook` the side-by-side stories. `docs/adr/` holds the decision
records, each with the evidence that settled it.

## Checks

```bash
pnpm check          # typecheck + API freshness + lint + gates + unit tests
pnpm gates          # the port's own quality bars, see below
pnpm test           # unit tests, no GPU needed
pnpm format         # prettier
PARITY_GPU=hardware pnpm e2e   # Playwright on a real GPU; software is refused
```

Everything except `pnpm e2e` runs without a GPU and is what CI runs.

Full standalone recipe qualification is opt-in:
`pnpm pack:qualify ./three-clouds-webgpu-0.1.0.tgz --keep-projects`.
It requires Node 24, pnpm 11.8.0 and network access on a cold package store.
It is not part of the default Vitest suite and proves CPU installation and
builds, not rendered frames.

`pnpm gates` is four checks this port holds itself to, and they are the bar a
change has to clear:

| Check | Bar |
| --- | --- |
| `oxlint` | cyclomatic complexity ≤ 13 per function |
| `decision-points.mjs` | ≤ 12 decision points per TSL `Fn` body, no unmeasured `Fn`, no control flow outside one |
| `comment-audit.mjs` | reports the comment-to-code ratio per file |
| `citations.mjs` | the attribution header on every ported file, the upstream citations in place, and the `TODO(port)` register intact |

The last one is a hard gate. Every file under `src/` starts with

```ts
// Ported from @takram/three-clouds (MIT, Copyright (c) 2024 Shota Matsuda)
// https://github.com/takram-design-engineering/three-geospatial
```

and keeps the citation URL next to the function it came from. A new ported
file needs that header; a glue file needs to be added to the allowlist in
`scripts/port-gates/required-citations.json` rather than left headerless.

## The parity harness

`examples/parity` renders the WebGL original (side A) and the port (side B) in
one page and compares them. It is the reason the port can claim parity rather
than resemblance.

```bash
pnpm --filter parity dev   # then open http://localhost:5173/?case=<name>
PARITY_GPU=hardware pnpm --filter parity capture --phase 1
```

Things worth knowing before you touch it:

- **Captures need a real GPU.** A software backend is refused. Metrics under
  `parity/results/` are committed evidence, regenerated by re-capturing a
  phase, never hand-edited. `scripts/verify-results.mjs` re-evaluates them
  against `thresholds.json`, and CI runs that.
- **A picture with an experiment on is not the reference contract.** Every
  opt-in option in `CloudsContext.experimental` defaults to `false` and must stay
  that way; the list is `experimentalDefaults` in
  `src/experimental/options.ts`, and each is documented in
  [docs/EXPERIMENTAL.md](docs/EXPERIMENTAL.md).
- **When a picture changes, re-capture and say so.** Include the before and
  after metrics in the PR. A change that moves a case below its threshold is
  either accepted in `thresholds.json` with a written reason or reverted.

## Code conventions

- Prettier decides formatting: no semicolons, single quotes, 2 spaces, 80
  columns. Run `pnpm format` rather than hand-formatting.
- Comments say *why* or cite. At most 3 lines for a line comment, 5 for a file
  header, 5 per JSDoc section. No em dashes, no trailing full stops, no comment
  on the same line as the code. `eslint` enforces this with
  `eslint-plugin-no-comment-slop`, so a chatty comment fails `pnpm lint`.
- JSDoc belongs on the public surface only: `CloudsContext`,
  `CloudsPassNode`, `clouds()`, `CloudLayer`, `CloudLayers`, the quality preset
  keys, and the texture loaders. Everywhere else, a line comment.
- Every shader `Fn` ships a CPU twin and a compiled-WGSL snapshot next to it.
  The twins use `test/helpers/cpuTwin.ts` and the snapshots
  `test/helpers/compileWGSL.ts`, so a maths change is checkable without a GPU.
  Log what the test computed; `test/helpers/log.ts` writes the table.

TSL has three rules that account for most of the bugs this port has had, and
they are worth reading before writing a shader:

- A `Fn` returns exactly one node. Return a `struct()` or a vector, never a
  plain JS object.
- Anything that reads screen-space derivatives or samples a texture
  implicitly (`texture(tex, uv)`) needs uniform control flow. Inside an `If`,
  a loop or a `Break`, WGSL leaves the value undefined. Hoist derivatives into
  variables above the branch and use an explicit level when sampling.
- A node a consumer captures before its producer has built reads a stale or
  zero value. A producer's public node must exist from construction and be
  filled in later.

## Proposing a change

- Open a pull request against `main`. One concern per PR, and a description
  that says what you measured.
- Small fixes need no ceremony. A change to a public property name, to a
  quality default, to the render graph, or to an acceptance threshold needs an
  ADR under `docs/adr/` (next free number, four headings: Context, Decision,
  Consequences, and whatever else the decision needs) written before or with
  the change.
- If a change alters pixels, attach the parity numbers for the cases it
  touches. If it alters performance, say the measurement method: what was
  compared, on what hardware, how many samples.
- If it fixes a bug, add the test that fails without the fix.
- Attribution is not optional. New code ported from the original keeps the
  header and the citation, and the upstream `TODO`/`NOTE` comments survive the
  port as `TODO(port):` markers. Do not remove either to satisfy a linter.
